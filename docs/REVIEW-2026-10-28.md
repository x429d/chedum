## 2. Краткое описание системы (для наблюдателя, видящего проект впервые)

Chenal — локальное macOS-приложение для импорта шахматных партий с Chess.com, разбора их
встроенным Stockfish и визуальной аналитики. Интернет используется только для публичного
Chess.com PubAPI; всё остальное — офлайн.

```text
SolidJS UI (views → components → stores → services/api.ts)
        │ Tauri IPC, типизированные DTO (camelCase)
        ▼
commands/*.rs — тонкие хендлеры (валидация + вызов сервиса)
        ├── service/    импорт PGN, оркестрация анализа
        ├── engine/     дочерний Stockfish, UCI, Mutex, throttle 75 ms
        ├── chesscom/   PubAPI, 1 req/s, 429 backoff, инкрементальные архивы
        ├── pgn/        pgn-reader, [%clk], writer
        ├── analytics/  Win%, accuracy, ACPL, Elo, 11 категорий, фазы, coach
        ├── db/         SQLite WAL, миграции, репозитории, SQL-агрегации
        └── domain/     модели, AppError → {code, message}
```

**Заявленные возможности** (из `README.md`): библиотека с фильтрами и синхронизацией,
студия разбора с SVG-доской и шестью наборами фигур, график Win% + время, точность по
методу Lichess, ACPL, performance Elo, 11 категорий ходов, Move Coach, Retry Mistake,
Player Hub, 3 865 линий ECO, четыре демо-партии.

**Фактический объём:** 7 472 строки Rust, 6 532 строки TS/TSX, 2 307 строк CSS,
25 коммитов за 26–28.10.2026, 84 Rust-теста, 0 фронтенд-тестов.

### 3.3. Что не проверялось (остаточный риск)

1. Ручной прогон интерфейса: темы, drag-and-drop, клавиатура, пустые состояния.
2. Живая синхронизация с Chess.com: сеть, `429`, поведение при смене ника.
3. Запуск `.app` на машине без Homebrew и без Stockfish.
4. Убийство процесса движка и выход из приложения во время анализа.
5. Полный прогон анализа 839 партий: оценка времени расчётная, не измеренная.
6. Безопасность WebView как пентест; проверено только отсутствие CSP.
7. Лицензионная экспертиза GPLv3 для Stockfish и SVG-наборов.

## 6. Реестр находок

Формат: ID, серьёзность, доказанность, описание, доказательство, влияние, рекомендация.

### 6.1. S2 — существенные

---

**F-01. Библиотека разобрана на 2.7 %, механизм полного разбора отсутствует**

- **Доказанность:** подтверждено (SQL + код).
- **Доказательство:** 839 игр, 23 анализа; `service/analysis.rs:97` пишет анализ одним
  вызовом после всех позиций; очередь живёт в `stores/libraryBatch.ts` и не сохраняется.
- **Влияние:** Hub, тренд, фазы, дебютная матрица и любые агрегаты описывают 2.7 % данных;
  выводы статистически нерепрезентативны. Выход из приложения посреди партии теряет работу.
- **Рекомендация:** персистентная очередь (`analysis_jobs`), чекпоинты, resume, фоновый
  воркер; затем полный прогон.

---

**F-02. Анализы выполнены на разных глубинах; средние смешивают несравнимые числа**

- **Доказанность:** подтверждено.
- **Доказательство:** `game_analyses.depth` = 21×14, 1×18, 1×22; в настройках сейчас
  depth 18, MultiPV 3.
- **Влияние:** средняя точность и ACPL по хабу некорректны; сравнение партий между собой
  некорректно.
- **Рекомендация:** хранить и показывать `depth/multipv/algo` per analysis; агрегировать
  только по одной глубине либо явно помечать смешанные значения.

---

**F-03. Нет происхождения метрик в модели и UI**

- **Доказанность:** подтверждено.
- **Доказательство:** `accuracy_algo` хранится глобально в `app_settings`;
  `AnalysisHeader` не показывает depth/multipv/algorithm.
- **Влияние:** после смены алгоритма старые и новые значения снова смешаются; потребитель
  не может проверить, чем получено число.
- **Рекомендация:** версионировать алгоритм per analysis; выводить метаданные в отчёте и
  экспорте.

---

**F-04. Агрегации Hub не ограничены аккаунтом**

- **Доказанность:** подтверждено.
- **Доказательство:** `db/stats_repo.rs:33,110,179` — фильтр только
  `user_color IN ('white','black')`; `GameFilter` не содержит `username`.
- **Влияние:** при двух аккаунтах или импортированных чужих PGN статистика смешивается,
  выводы неверны.
- **Рекомендация:** ввести профиль/аккаунт в модель, фильтровать все агрегаты и библиотеку.

---

**F-05. Тренд точности берёт первые 200 партий, а не последние**

- **Доказанность:** подтверждено.
- **Доказательство:** `db/stats_extra.rs:13` — `ORDER BY g.played_at ASC LIMIT 200`.
- **Влияние:** при росте числа анализов график «застынет» на самых старых партиях.
- **Рекомендация:** `ORDER BY played_at DESC LIMIT 200` с разворотом для отображения.

---

**F-06. Цвет игрока в агрегатах определяется чётностью полухода, а не позицией**

- **Доказанность:** подтверждено (механизм), воспроизведение на FEN-партии не выполнено.
- **Доказательство:** `db/stats_repo.rs:213`, `db/stats_extra.rs:64`,
  `db/analyses_repo.rs:314` — `ply % 2`; при старте с FEN и ходе чёрных чётность
  инвертируется.
- **Влияние:** точность и тайм-статистика считаются не для того игрока в партиях с
  нестандартной начальной позицией.
- **Рекомендация:** хранить `player_color` в `move_evaluations` либо вычислять из
  `initial_fen` + ply.

---

**F-07. Упавший движок не перезапускается до перезапуска приложения**

- **Доказанность:** подтверждено кодом, поведение не воспроизводилось.
- **Доказательство:** `engine/state.rs:15` — `OnceCell<EngineManager>` без сброса;
  ошибка чтения/записи оставляет мёртвый процесс в кеше.
- **Влияние:** после сбоя Stockfish любой анализ возвращает ошибку до рестарта.
- **Рекомендация:** сбрасываемый слот + один автоматический retry + понятное сообщение.

---

**F-08. Ошибки разбора при синхронизации маскируются под дубликаты**

- **Доказанность:** подтверждено.
- **Доказательство:** `chesscom/sync.rs:127` — `None` от `remote_to_draft`
  (вариант/нелегальный PGN) увеличивает `games_skipped` наравне с дедупликацией.
- **Влияние:** пользователь видит «пропущено N», но не знает, что часть партий не
  импортирована из-за ошибок; данные тихо теряются.
- **Рекомендация:** разделить счётчики `duplicates` и `errors`, показывать причины.

---

**F-09. Блокирующий SQLite внутри async-команд**

- **Доказанность:** подтверждено кодом.
- **Доказательство:** `Db` — `std::sync::Mutex<Connection>`; `commands/games.rs:12` и
  другие `async fn` вызывают `rusqlite` напрямую.
- **Влияние:** длинные запросы/импорт занимают токио-воркер; при синхронизации и больших
  выборках возможны подвисания UI.
- **Рекомендация:** `spawn_blocking` или пул соединений; для записи — батчи в транзакции.

---

**F-10. «Автоанализ» после импорта обрабатывает только текущую страницу**

- **Доказанность:** подтверждено.
- **Доказательство:** `stores/libraryStore.ts:169` — `games()` возвращает текущую
  страницу (25/50/100), а не всю библиотеку.
- **Влияние:** после синхронизации 839 партий автоматически разбираются максимум 25.
- **Рекомендация:** запрашивать id всех неразобранных партий отдельным запросом.

---

**F-11. Тренажёр ошибок не сохраняет прогресс**

- **Доказанность:** подтверждено.
- **Доказательство:** `components/analytics/RetryTrainer.tsx:17–20` — `index`, `attempts`,
  `solved` объявлены локальными сигналами; при уходе с экрана сбрасываются.
- **Влияние:** нет банка ошибок, повторений, статистики; функция не выполняет роль
  тренажёра, заявленную в README.
- **Рекомендация:** таблица `training_items` + SRS, сессии и прогресс.

---

**F-12. Метрика точности расходится с Chess.com; число Chess.com выбрасывается**

- **Доказанность:** подтверждено (код + документ проекта).
- **Доказательство:** `chesscom/client.rs` — `RemoteGame` не содержит `accuracies`;
  `docs/ACCURACY-PARITY.md` фиксирует r 0.964 → 0.634 и σ 12.7 после перехода на Lichess.
- **Влияние:** пользователь видит число, которое не совпадает с привычным ему Chess.com и
  хуже ранжирует партии; доверие к аналитике падает.
- **Рекомендация:** сохранять `accuracies` из PubAPI, показывать обе шкалы с пояснением,
  зафиксировать каноническую метрику.

## 8. Архитектурная оценка

### 8.1. Сильные стороны (подтверждено)

1. **Слои.** `invoke` только в `services/api.ts`; команды тонкие; бизнес-логика в сервисах
   и `analytics`; `lib.rs` собирает приложение.
2. **Ошибки.** Единый `AppError` с машинным кодом и сериализацией во фронтенд.
3. **Движок.** `kill_on_drop`, `Drop`-килл, `stop()` через `AtomicBool`, таймаут 120 с,
   throttle 75 мс, graceful shutdown с таймаутом 3 с.
4. **Данные.** WAL, FK, `user_version`, транзакционные батчи, дедупликация по
   `external_id`, каскадное удаление.
5. **Честность метрик.** Отдельный документ с замерами и пересчёт без движка по версии
   алгоритма.

### 8.2. Слабые стороны (подтверждено)

1. Один движок и один флаг отмены на все сценарии; бэкенд не запрещает параллельные
   вызовы, они встают в очередь на мьютексе.
2. Синхронная БД в async-командах (F-09).
3. Нет персистентной очереди и чекпоинтов (F-01).
4. Нет провенанса метрик (F-02, F-03).
5. Нет автоматической регрессии фронтенда (F-14).

надстраиваются над недостоверными данными. B и C независимы друг от друга и могут
выполняться параллельно после A.
